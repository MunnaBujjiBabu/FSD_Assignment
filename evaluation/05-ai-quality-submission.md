## 5.4 Reflection (1–2 pages)

### Did AI help or hinder understanding?
AI accelerated **scaffolding** — Express services, React routes, SQLite seed, OpenAPI — letting effort focus on the **architecture and integration**. To genuinely understand the system, I read each generated file and traced the request lifecycle from React → Gateway → Service → DB. The biggest learning came from **debugging**, not from generation.

### Issues encountered integrating AI output
- **Gateway path rewrite bug.** AI’s first version stripped `/api` instead of mapping to each service’s prefix; login returned `Cannot POST /login` from the auth-service. Fixed by rewriting the proxy to `/auth${path}` etc. (See commit history.)
- **`express.json()` on the proxy** would consume request bodies before forwarding. Removed it — the gateway only proxies; downstream services parse JSON themselves.
- **Permission/PATH issues with `npm`** in the local environment. Solved by running services directly with `node` and fixing `~/.npm` ownership.
- **Cross-service stock mutation** needed a `SERVICE_KEY` to prevent unauthorized updates — added during review.

### What I learned from debugging AI-generated code
- The importance of testing each layer in isolation (`curl` to service vs. via gateway) to localize issues.
- Why an **API gateway** is a great auth choke-point — services stay simple and replaceable.
- Trade-offs between **denormalized snapshots** (e.g., `book_title` in reservations) and strict normalization across services.
- Always re-read AI code; helpful but not infallible.

### Manual vs AI workflow
| Aspect              | Manual Only           | With AI (Copilot)                          |
|---------------------|------------------------|--------------------------------------------|
| Scaffolding time    | Hours                  | Minutes                                    |
| Boilerplate quality | Variable               | Consistent, idiomatic                      |
| Debugging insight   | Built-in via writing   | Required intentional review of generated code |
| Documentation       | Often skipped          | Easy to generate Swagger/Mermaid           |

### Limitations of AI observed
- AI assumes a “best-case” environment — local tooling/permission issues still need a human.
- Generated code can over-engineer or include benign extras; trimmed during review.
- AI cannot verify runtime behavior — I still had to run, click, and test the flow end-to-end.

## 5.5 Code Quality Practices

- **Separation of concerns**: each microservice handles a single bounded context.
- **Reusable shared utilities**: `shared/db.js`, `shared/auth.js`.
- **Explicit role checks** at service boundaries.
- **Standardized JSON error responses** with proper HTTP status codes.
- **Consistent naming and module patterns** across services.
- **Modular React components** + centralized API client.
- **`.gitignore`** excludes `node_modules`, SQLite DBs, build outputs, secrets.
- **`.env.example`** documents required environment variables.
- **OpenAPI spec** stays close to the implementation.
- **Manual sanity check**: `node --check` on all backend JS files passed.

## 5.6 Git Commit Hygiene

- Repository: https://github.com/MunnaBujjiBabu/FSD_Assignment
- Conventional, descriptive commit messages, e.g.:
  - `Initial commit: E-Library Reservation System (...)`
  - `docs: expand root README with setup, usage, API, and troubleshooting`
- `main` branch tracks `origin/main`; clean working tree after each push.
- No secrets committed; sample credentials only.

To inspect history locally:
```bash
git log --oneline --decorate --graph
```
